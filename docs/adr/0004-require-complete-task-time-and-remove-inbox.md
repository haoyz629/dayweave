# 正式任务要求完整时间并移除 Inbox

## Context

Inbox 与持久化任务草案都承担“信息尚未完整、之后再处理”的职责，用户需要理解两套近似队列。与此同时，无日期正式任务不能直接进入日计划，实际仍需再次补全开始与结束时间。保留 Inbox 因而增加状态和入口，却没有形成独立、不可替代的工作流。

## Decision

- 删除 Inbox 产品状态、筛选、计数和操作入口。
- 普通任务只有在开始日期、开始时间、结束日期、结束时间全部存在，且时间范围有效时，才允许经用户确认创建为正式任务。
- 缺少任一时间字段的手动或 AI 内容可以持久化，但只能保持为任务草案；不得进入正式任务表、月历或日计划候选。
- 正式任务后续编辑同样不得保存不完整或无效的时间范围。
- 界面的“清除时间”可以清空草稿的四个时间字段，但不得借此把既有正式任务保存为不完整状态；正式任务编辑未补全前只能保持为未提交表单，SQLite 中原任务不变。
- 历史 `inbox` 任务迁移为 `open`，保留任务 ID、来源、内容和变更历史，不猜测或补造时间；补全时间前，计划层必须排除这些兼容数据。
- 已在回收站、且恢复状态为 `inbox` 的历史任务，其恢复状态迁移为 `open`；保存的 Inbox 筛选偏好迁移为待处理筛选。
- 前端校验用于及时反馈，Rust 领域校验和 SQLite 事务仍是最终约束；旧 AI 直接创建入口也必须服从完整时间规则。

## Consequences

- “草案”成为所有信息不完整任务的唯一暂存位置，任务页的信息架构更简单。
- 待处理任务表示“已确认且时间完整、尚未进入日计划”，不再混入未定时间事项。
- 同日任务的预计投入由完整起止边界自动计算；清除边界后该计算失效，界面必须提示补全而不是保留一个看似有效的正式任务。
- 历史无时间任务可继续查看和补全，但在补全前不能参与自动或手动日计划确认。
- 基础 SQLite 表为兼容旧数据库仍可保留历史 `inbox` 棘轮值；运行时领域模型不再暴露该状态。
