# Apple 日历式重叠事项布局设计

> 2026-11-28 状态说明：非独占重叠排布原则（[ADR-0003](adr/0003-adopt-non-exclusive-daily-timeline.md)）继续有效；在当前 v2 实现（`src/utils/timelineLayout.ts` 的 `layoutOverlappingItems`）中，重叠时间块采用**连通分量贪心分列并等分宽度（`100% / totalCols`）**，不再执行向右跨列扩展。本文保留为历史布局算法设计参考。

## 定位

本设计参考 Apple 日历日视图中可观察到的阅读方式：时间决定纵向位置，同时发生的事项横向避让，较长事项形成稳定锚点，空出的横向空间可由没有冲突的事项利用。Apple 没有公开其完整布局算法，因此本文定义的是适合今序的 **Apple-inspired** 规则，不宣称复刻 Apple 的内部实现。

这是一套视觉布局规则，不改变非独占日程领域模型。固定日程、执行块、日计划草案块和有展示时间的重复事项仍可处于同一时段；“重叠”不是保存错误，“包含”也不是父子关系。

## 要解决的问题

当前规则只说明同一耦合组稳定分列，却没有回答以下问题：

- 一个短事项完全落在长事项的时间范围内时，是并排、覆盖还是嵌套；
- 一个耦合组只在局部达到三列时，其余事项是否仍被压成三分之一宽；
- 同起点但时长不同的事项，哪一个保持左侧锚点；
- 极短事项如何保持真实高度，并避免把相邻时间误判为重叠；
- 刷新、SQLite 重新读取或数据来源顺序改变后，事项是否会随机换列。

设计目标是让用户只看空间关系就能理解“何时同时发生”，同时让同一组事项在刷新前后保持稳定。

## 术语

**实际区间**：事项保存的半开时间区间 `[start, end)`。只有 `a.start < b.end && a.end > b.start` 才构成真实重叠；`A.end == B.start` 是首尾相接，不是重叠。

**时间包含**：一个事项的实际区间完整位于另一个事项内。例如 A 为 `09:00 - 12:00`，B 为 `10:00 - 11:00`。它只描述时间关系，不表示 B 属于 A。

**绘制区间**：事项按照实际区间等比例映射到时间轴；不设置最小视觉时长。极短事项可以收起次要文字，但卡片本身不得放大。

**布局碰撞**：两个事项的实际区间相交。真实时间不重叠的事项不得因为视觉可读性需要而被判为碰撞。

**耦合组**：通过布局碰撞直接或间接连接起来的一组事项。上午与下午互不连接的两组事项必须独立计算，不能共享列数。

**基础列**：稳定分列后分配给事项的起始列。

**横向扩展**：事项保持基础列不变，在自身整个实际区间内没有碰撞时，向右占用连续空列。横向扩展不向左发生，也不产生中途变宽的 L 形卡片。

## 空间规则

### 1. 所有定时事项共用一套布局

以下对象统一进入同一计算入口：

- 固定日程；
- 已确认执行块；
- 日计划草案块；
- 有展示时间的重复事项。

对象类型只影响卡片内容、颜色和交互，不影响列优先级。不得为重复事项或固定日程保留独立半宽轨道。

全天事项和无展示时间的重复事项位于时间轴上方，不参与小时轴分列。

### 2. 排序必须确定

每个耦合组按照以下顺序分配基础列：

1. 实际开始时间升序；
2. 开始时间相同时，实际结束时间降序，较长事项优先成为左侧锚点；
3. 起止时间都相同时，按稳定对象键排序，例如 `event:<id>`、`block:<id>`、`draft:<stable-id>`、`recurring:<id>`。

稳定对象键只负责打破平局，不能按对象类型人为改变左右顺序。日计划草案必须具有刷新后可复现的稳定键，不能只依赖临时数组位置。

### 3. 基础列使用“最早可复用列”

依次处理排序后的事项，将事项放入第一条满足 `该列最后实际结束 <= 当前实际开始` 的列；如果没有可复用列，则新增一列。

该规则带来以下结果：

- 完全相同的时间段自然等分；
- 首尾相接的事项可以复用列；
- 链式重叠保持稳定列，不因只比较相邻元素而漏判；
- 极短事项仍按真实区间判断，相邻但不重叠时复用同一列。

### 4. 列数由耦合组的最大真实并发决定

耦合组的基础列总数等于该组内真实重叠所需的最少列数。独立耦合组分别计算列数。

这不意味着组内每个事项都必须永久保持 `1 / 总列数` 的宽度。基础列完成后，还要执行横向扩展。

### 5. 事项只向右扩展到安全边界

从事项的基础列开始，逐列检查右侧相邻列：如果目标列中没有任何事项在当前事项的整个实际区间内与它碰撞，则当前事项可以占用该列；遇到第一条有碰撞的列立即停止。

扩展后的事项仍是一个左边界、宽度和高度均固定的矩形：

- 不向左扩展，避免刷新后横向起点跳动；
- 不在时间中段改变宽度，避免形成难以点击和阅读的 L 形轮廓；
- 不覆盖其他事项，选中态提高层级也不能改变几何范围；
- 同一组局部曾出现三列，不代表其他时段的事项都只能使用三分之一宽。

### 6. “时间包含”必须表现为并列，不是卡片嵌套

当 B 的时间被 A 包含时，A 与 B 分配到不同基础列。A 保持完整纵向长度，B 出现在对应时间高度的另一列。

两张卡片使用同一画布坐标系和同等级边界，不增加表示父子关系的内缩、包裹容器、背景层或连接线。用户看到的是“B 在 A 进行期间发生”，而不是“B 属于 A”。

### 7. 完全相同时间必须严格等分

2、3、4 个起止完全相同的事项分别占用 `1/2`、`1/3`、`1/4` 可用宽度，间距一致，任何事项都不能横向扩展。

卡片内容优先级为：

1. 对象标识：普通执行块勾选或重复事项右上重复图标；
2. 标题；
3. `起 - 止`；
4. 状态、说明、预计时长等补充信息。

列变窄时先省略补充信息，标题始终保持单行并使用省略号；对象标识不得消失。完整标题和内容由统一悬浮卡、原生标题提示或键盘聚焦说明提供。

## 典型布局矩阵

| 场景 | 输入 | 基础列 | 扩展结果 |
|---|---|---:|---|
| 无重叠 | A `09:00-10:00`，B `10:00-11:00` | 1 | A、B 均全宽 |
| 完全相同 | A/B/C `09:00-10:00` | 3 | 三项各占三分之一 |
| 部分重叠 | A `09:00-10:30`，B `10:00-11:00` | 2 | A、B 保持左右两列 |
| 时间包含 | A `09:00-12:00`，B `10:00-11:00` | 2 | A 左、B 右，各占一半；不存在视觉嵌套 |
| 链式重叠 | A `09:00-10:00`，B `09:30-10:30`，C `10:00-11:00` | 2 | A 与 C 复用左列，B 使用右列 |
| 局部三列 | A `09:00-12:00`，B/C `09:00-10:00`，D `10:00-11:00` | 3 | A 占左侧三分之一；D 可从中列向右扩展为三分之二 |
| 独立分组 | 上午 A/B 重叠，下午仅 C | 上午 2、下午 1 | 上午各半，下午 C 全宽 |
| 极短相邻 | A `09:00-09:05`，B `09:05-09:10` | 1 | 两项高度各为 5 分钟并复用同一全宽列 |

## 示意

### 时间包含

```text
09:00  ┌──────── A 09:00-12:00 ───────┐
10:00  │                               │ ┌── B 10:00-11:00 ──┐
11:00  │                               │ └────────────────────┘
12:00  └───────────────────────────────┘
```

A 与 B 是并列矩形。B 的纵向位置位于 A 的时间范围内，但 B 不绘制在 A 的 DOM 或视觉容器内部。

### 局部三列后的安全扩展

```text
09:00  ┌──── A ────┐ ┌──── B ────┐ ┌──── C ────┐
10:00  │            │ ┌──────── D 可扩展 ────────┐
11:00  │            │ └───────────────────────────┘
12:00  └────────────┘
```

D 的左侧基础列保持不变；因为右列在 D 的时间范围内为空，D 可以占用右侧空间。

## 视觉与交互边界

- 所有卡片之间保留一致的细间距，扩展后也不能贴合成一张大卡片。
- 固定日程、执行块、草案块和重复事项继续使用各自已确认的视觉语言；布局算法不得改变普通执行块左上勾选或重复事项右上图标的位置。
- 普通任务块不得短于 15 分钟；计划草案块和已确认执行块在 15–29 分钟时共用单行标题并隐藏时间行，只有已确认执行块保留缩小后的勾选；30 分钟及以上恢复双行信息和对应状态下的标准控件。固定日程、重复事项等非普通任务对象仍可短于 15 分钟。
- 任务块内容容器必须设置可收缩宽度与安全溢出边界；标题使用单行省略，左上勾选或右上对象图标不得覆盖标题。今日页待安排胶囊使用自然高度承载标题、摘要和元数据，不以固定高度裁切内容。
- 选中、悬停与键盘聚焦只能提升描边、说明和层级，不得改变列、宽度或导致其他事项重新排版。
- 胶囊快捷操作只在悬停或真正的 `focus-visible` 状态出现；鼠标点击后不得因 `focus-within` 长期占据标题区域。
- 所有类型的卡片高度严格按实际时长等比例绘制；极短卡片空间不足时收起次要文字，完整内容由悬停或键盘聚焦说明提供。
- 当前时间红线位于所有事项之上，但不截断事项的点击区域。
- 窄窗口和 Windows 高缩放下仍保持相同算法；不因空间不足退化为互相覆盖。必要时减少卡片正文，只保留标识、标题和时间。
- DOM 与键盘焦点顺序遵循确定性排序，而不是横向扩展后的视觉面积。

## 非目标

- 不复制 Apple 的配色、字体、阴影或圆角；今序继续使用自己的设计系统。
- 不按任务优先级、状态或对象类型决定左右列。
- 不把重叠解释为冲突、占用或需要用户确认的异常。
- 不绘制一张事项在不同时间段宽度变化的多边形。
- 不因为视觉扩展修改 SQLite 中的起止时间、工作量、任务状态或执行事实。

## 实施交接

实现应把布局结果从 `{ column, total }` 扩展为至少 `{ column, columnSpan, total }`，其中：

- `column` 来自确定性基础列分配；
- `columnSpan` 来自向右安全扩展；
- `total` 是当前耦合组的基础列总数；
- 位置计算使用 `(column, columnSpan, total)` 生成固定矩形；
- 布局函数应保持纯函数，使用表驱动测试覆盖本文矩阵；
- 测试同时断言列分配、扩展跨度、无几何覆盖和输入顺序变化后的确定性。

该改动只属于前端布局，不需要修改 SQLite 模型、后端重叠合法性或 AI 确认边界。
