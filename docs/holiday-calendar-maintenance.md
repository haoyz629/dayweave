# 法定节假日数据发布与维护

## 来源和职责

以国务院办公厅正式年度放假安排通知为依据，维护者核对后发布完整年度数据。客户端不抓取通知网页，不预测调休，不把传统节日名称当作已经确认的放假日期。

年度 JSON 的 `from` / `to` 必须是该年 1 月 1 日和 12 月 31 日。这是维护者对全年已核对的声明，结构校验不能替代人工核对整份通知。

## 每年发布步骤

1. 官方通知发布后，复制 `data/holidays/2026.json` 为对应年份；填写全部放假日、全部补班日、来源通知链接及实际核对日期。`schemaVersion` 保持 1，新年份 `revision` 从 1 开始。
2. `version` 写清通知所属年份；`sourceUrl` 使用 HTTPS 的政府网站通知链接。日期必须为真实的 `YYYY-MM-DD`，不能跨出该年、重复或既放假又补班。`namedDate` 如填写，必须在对应组的放假日期内。
3. 在 `data/holidays/index.json` 增加该年记录：`year`、`revision`、固定 `path: "YYYY.json"`、相同的 `sourceUrl`、`verifiedAt`。不得填写外部地址、路径跳转或测试安排。
4. 逐项核对通知，尤其检查跨月假期、补班周末、同年更正。执行 `node --experimental-strip-types scripts/validate-holidays.mjs` 和相关 Node/Rust 测试，再审查差异。
5. 经授权后正常提交、推送到公开可读的分发分支。未授权不推送，不为此擅自将私有仓库公开。发布新年度 JSON 不要求重发客户端安装包。
6. 免登录访问线上 `index.json` 和年度 JSON，确认 HTTP 200、内容一致；在客户端手动检查并确认新年份覆盖、重启和断网可用。只完成本地测试不能宣称线上分发可用。

## 更正与兼容

- 已发布内容修改必须提高该年 `revision`，索引与年度文件保持一致；禁止同修订号修改内容，禁止降低修订号。
- 客户端校验整个批次后事务提交，异常、超时、结构不兼容或降级均保留原有效缓存；已缓存历史年份不会因从索引移除而被删除。
- 更高版本客户端内置的数据优于较旧缓存；不通过删除用户数据库来解决更新问题。
- 旧版客户端不认识新结构版本时保留旧数据并报告更新失败，不静默按新格式解释。
- 不发布虚构 2027 年测试安排；自动测试里的合成年度包仅存在于隔离测试。

## 首版固定分发地址

`https://raw.githubusercontent.com/haoyz629/dayweave/main/data/holidays/`

客户端固定请求 `index.json` 与 `YYYY.json`，不接受索引指定的其他主机，不跟随重定向。后台只下载公共日历文件，不上传任务或设置。自动检查最多每 24 小时一次；手动检查可重试。

本次实施时免登录请求该仓库 README 与日历索引均返回 **404**。这可能是仓库未公开、资源未发布或访问条件限制，不能据此认定线上已经可用。需要有权限的维护者提供可公开访问的静态分发位置；若另选地址，应同时修改后端固定源、这份说明并重新验证。不得把私人访问令牌内置进客户端。

## 数据行为边界

启动先用内置数据及本地已验证缓存，不等待网络。缺失年份的工作时间暂按用户每周设置；法定工作日重复规则要求从起点至目标日期涉及的每一年都有覆盖，缺口不作推测。补齐后恢复未落地的规则推演，不移动或删除已保存任务块、单次执行结果及历史。

节气表目前只覆盖 2026 年；此更新流程不承诺未来年份节气显示，也不新增跨年节气算法。
